**2. One AI-produced output that was wrong, and one thing I verified myself.**
Claude's first worker read messages in batches with getmany() and then called consumer.commit() with no arguments after the first message. That commits the position after the whole batch, so messages 2..n of a batch would have been marked as done before they were processed. This is exactly the "offset committed before processing" problem from Part 3 II. A second problem was in the first homework_demo.py: it sorted the merged client/API/worker log only by timestamp, and because several lines have the same millisecond, the API's "response received" line was printed before the worker's "reply sent" line, which looks impossible. I also verified one result myself instead of trusting the test script: for the consumer-death after-run I asked Kafka directly with kafka-consumer-groups.sh --describe for group s4098_writers_death_after_205809, and it showed CURRENT-OFFSET 1 = LOG-END-OFFSET 1 with lag 0 on partition 1, the same value the script reported "at the end".

**3. How the problems were found / how I verified.**
The batch-commit bug was found while reviewing the commit code against how aiokafka's commit() works without offsets (it commits the current position of every assigned partition). The log-order problem was visible in the first test output of the demo. For my own check I used the Kafka CLI on the real broker (Figure 22) and compared the committed offset with the message offset (0) and with the runner's value (1).

**4. What was changed and why it works now.**
Every consumer now commits exactly one message, commit({TopicPartition: msg.offset + 1}), and only after its output (response, plan, draft or final) was written with send_and_wait. In my consumer-death after-run the committed offset stayed at 0 after the kill, so the restarted Writer got the same message again and finished it; in the before-run (auto-commit) the offset was already 6 and the task was lost. The demo now orders the merged log by operation and by the stage of the round trip (client send -> API send -> worker receive/process/reply -> API response -> client) and keeps the real timestamps, so the sequence in Figure 11 is in the right order.
