**2. One AI-produced output that was wrong, and one thing I verified independently.**
Claude's first worker read messages in batches with `getmany()` and then called `consumer.commit()` with no arguments after the first message. That commits the position after the *whole* batch, so messages 2..n of a batch would have been marked done before they were processed - exactly the "offset committed before processing" bug that Part 3 II is about. A second problem was in the first `homework_demo.py`: it sorted the merged client/API/worker log only by timestamp, and because several lines share the same millisecond, the API's "response received" line appeared before the worker's "reply sent" line, which looks impossible.
Independently, I checked the consumer-death result with Kafka itself instead of trusting the test script: [FILL IN after running: the `kafka-consumer-groups.sh --describe` output for group `s4098_writers_death_after_<run>` showed CURRENT-OFFSET = ___, the same value the script reported "at the end"].

**3. How the problems were detected / how I verified.**
The batch-commit bug was found by reading the aiokafka semantics of `commit()` without offsets (it commits the consumer's current position for all assigned partitions) while reviewing the commit code; the fix was then tested with the consumer-death run. The log-order problem was visible in the first test output of the demo. For my own check I ran the Kafka CLI against the real broker and compared the committed offset with the runner's value and with the message offset it printed.

**4. What was changed and why it works now.**
Every consumer now commits exactly one message: `commit({TopicPartition: msg.offset + 1})`, called only after the output (response, plan, draft or final) was written with `send_and_wait`. In the consumer-death "after" run the committed offset stayed at the message's offset after the kill, so the restarted Writer received the same offset again and finished it; in the "before" run (auto-commit) the offset had already moved past the message and it was lost. The demo now orders the merged log by operation and by the stage of the round trip (client send -> API send -> worker receive/process/reply -> API response -> client), keeping the real timestamps, so the sequence is shown in causal order.
